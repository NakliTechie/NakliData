# NakliData observations and recommendations

Date: 18–19 August 2026

## Outcome

NakliData passed bounded live reads against Databricks SQL Warehouse and
Snowflake Virtual Warehouse through the packaged Cloudflare Worker Compute
Bridge. The exercise found two Worker-runtime incompatibilities and repaired
both with regression coverage.

The branded compute cards remain unavailable. Databricks now has live
multi-chunk, cumulative-limit, client-abort, and recovery evidence. Expiry,
throttling, and one post-repair live limit rerun remain. Snowflake now has
async polling, eight-partition assembly, cumulative limits, timeout, expiry,
direct denial, explicit cancellation, abort recovery, and revocation evidence.
Its live HTTP 429 remains. Iceberg REST catalogs remain a separate weekend
batch.

Detailed evidence: `docs/warehouse-live-matrix-2026-08-18.md`.

## Observations

1. The product boundary is right: browser-local work plus a customer-deployed,
   read-only bridge fits Databricks and Snowflake security expectations better
   than sending credentials or warehouse results through a NakliData service.
2. Vendor compatibility is a wire-level problem, not a logo-level problem.
   Databricks returned a nonstandard Arrow media type. Snowflake exposed an
   Apache Arrow implementation path that Worker runtimes cannot execute.
3. “Catalog” and “warehouse compute” must remain distinct in product copy.
   SQL Warehouse and Virtual Warehouse reads do not prove Iceberg REST,
   credential vending, or catalog interoperability.
4. Least privilege needs two proofs: the platform grant layout and an actual
   vendor-side write denial. Both live profiles now have both proofs.
5. Revocation behavior differs by vendor. Snowflake rejected the former JWT
   credential immediately after key removal and user disablement. Databricks
   continued accepting an already issued one-hour token after principal
   deactivation; secret deletion prevents renewal rather than invalidating that
   token.
6. Trial cost was bounded. Databricks compute was stopped immediately after the
   matrix. Snowflake showed its warehouse suspended and its full displayed
   trial balance remaining.
7. A 600,000-row Databricks request crossed three external Arrow chunks and
   returned 56.1 MB of assembled Arrow without exposing row values in evidence.
8. A real client disconnect recovered cleanly. Databricks recorded terminal
   `FINISHED`, not `CANCELED`, because the bounded query won the cancellation
   race.
9. The 1 MiB live limit exposed split budget ownership: the response layer
   rejected the oversized result after the vendor adapter used its larger
   default. Both vendor factories now receive the runtime byte and deadline
   ceilings.
10. Vendor authentication and throttle failures need stable public
    classifications. Both adapters now preserve redacted 401 and 403 outcomes.
    Databricks and Snowflake retain their distinct 429 paths instead of
    collapsing these cases into a generic upstream error.
11. Snowflake's partition metadata is operationally important. A 300,000-row
    result used eight JSONv2 partitions before the bridge emitted 47.9 MB of
    Arrow, so first-page success is not a completeness test.
12. Cancellation has two separate claims. A client abort can recover after the
    provider query reaches `SUCCESS`; an explicit cancel can still reach
    terminal SQLSTATE `57014`.
13. Bridge authentication and warehouse authentication need separate names.
    The browser may hold `BRIDGE_AUTH_TOKEN` under the disclosed source-secret
    policy. Databricks and Snowflake tokens stay inside Worker secret bindings.
    Strict configuration parsing now rejects undeclared fields at every level.
14. Worker result bytes are not the same as peak heap. Both vendor paths retain
    inputs while constructing Arrow output. Cloudflare's 128 MiB memory limit
    needs a deployed staging run at the intended result cap before release.
15. Snowflake's original UTF-8 path allocated one buffer per cell. Direct
    `encodeInto` writes cut the same 8.99 MB fixture's retained RSS delta by
    more than 67 percent while preserving Unicode and null semantics.

## Recommendations

### P0 — finish the two compute matrices

- Treat Databricks as setup and verification infrastructure only. Consume the
  existing trial balance. Do not add payment, upgrade, or paid capacity.
- Databricks: prove expiry and throttling. Repeat the 1 MiB live limit after
  runtime-budget propagation. Require provider `CANCELED` only if terminal
  `FINISHED` after a real client abort is insufficient for the release claim.
- Snowflake: prove a live HTTP 429 without unsafe request pressure. Treat a
  provider-cancelled client disconnect as optional unless release copy names
  that exact behavior.
- Keep each branded card independently gated. A Databricks pass must not unlock
  Snowflake, and the reverse must also hold.
- Keep the initial Worker result cap at 32 MiB until a deployed staging run
  measures peak heap through both vendor conversion paths.

### P0 — retain the repaired Worker compatibility boundaries

- Keep Databricks signed-result requests credential-free and redirect-manual.
- Accept only the three observed/standard Arrow media types.
- Keep Snowflake JSONv2 conversion free of runtime string compilation.
- Add a live-profile fixture to every future dependency upgrade involving
  Apache Arrow, Wrangler, Workerd, or either vendor API.

### P1 — package deployment without weakening ownership

- Publish the Compute Bridge as a versioned customer-deployed Worker only after
  the matrices pass.
- Require the post-deployment smoke to match the exact intended bridge version;
  a protocol-compatible stale Worker is not acceptable release evidence.
- Provide copy-paste configuration templates that contain no credentials.
- Set secrets interactively through Wrangler or the customer's secret manager.
- Default every environment to `unconfigured` and require an explicit
  read-only-identity assertion backed by deployment evidence.
- Document install, upgrade, rollback, key rotation, cancellation, and cost
  ceilings before enabling product cards.

### P1 — run catalog work as a separate release train

- Databricks: Unity Catalog Iceberg REST on the approved AWS-backed profile,
  including OAuth/PAT failure, prefix routing, pagination, vended S3
  credentials, refresh, cancellation, and zero writes.
- Snowflake: Open Catalog/Polaris on S3 or GCS, including OAuth refresh,
  credential lifecycle, pagination, refresh, cancellation, and zero writes.
- Keep Azure/ADLS unavailable until a separately pinned runtime profile and
  live matrix exist.

### P1 — use vendor-native vocabulary precisely

Databricks terms worth covering in UI help and search aliases:

- Unity Catalog, metastore, catalog, schema, table, volume;
- SQL Warehouse, serverless warehouse, Statement Execution API;
- service principal, OAuth M2M, workspace entitlement, `CAN USE`;
- Delta table, Delta Sharing, Iceberg REST, credential vending;
- metric view, expectation, lineage, system tables.

Snowflake terms worth covering:

- Horizon Catalog, database, schema, table, view;
- virtual warehouse, auto-suspend, resource monitor;
- service user, role, key-pair JWT, imported privileges;
- Open Catalog, Apache Polaris, catalog integration;
- semantic view, Data Metric Function, masking policy, row access policy;
- query history, result partitions, SQL API, streams and tasks.

Use these as aliases and explanations only where NakliData has a real adjacent
job. Do not imply governance enforcement, warehouse administration, catalog
interoperability, or orchestration without the corresponding artifact and
live gate.

## Immediate sequence

2. Finish Databricks expiry, throttling, and the post-wiring live limit rerun
   under a fresh short-lived secret.
3. Find a low-pressure, vendor-supported way to produce Snowflake HTTP 429.
4. Run the full repository gate.
5. Enable only the profile whose complete matrix passes.
6. Take up Databricks Unity Catalog and Snowflake Open Catalog/Polaris in the
   scheduled weekend catalog batch.
