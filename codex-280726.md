# NakliData observations and recommendations

Date: 28 July 2026
Review focus: technical trustworthiness and positioning for Databricks and Snowflake users

The product has a differentiated core: browser-local analysis, semantic
classification with evidence, data-quality assertions, lineage, deterministic
cleaning, portable reports, and a constrained BYOK sidecar. The strongest
position remains:

> A local inspection, semantic-contract, and data-quality workbench beside
> Databricks or Snowflake.

It is not ready to lead with direct lakehouse/warehouse connectivity. The two
most market-relevant connection stories are currently incomplete:

- Iceberg URL and REST Catalog are prominent, but both mount paths always fail in
  this build.
- Compute Bridge has a working browser protocol client, but no supported bridge
  binary, image, installer, or branded Databricks/Snowflake adapter ships with the
  product.

The full evidence, severity ranking, and implementation workplan are in
[`plan/_archive/forward-pass-2026-07-28.md`](plan/_archive/forward-pass-2026-07-28.md).

## Most important observations

### 1. Fix trust boundaries before adding platform presets

Two issues are release blockers:

- Agent query redaction can be bypassed with SQL aliases/expressions and fails
  open when the sensitivity layer is unavailable.
- A malformed `.naklidata` file can clear the live workspace before validation
  fails, and autosave can persist the partial state.

Other high-priority trust gaps affect sessions, source naming, S3 credentials,
anonymized exports, and CSV formula safety. Enterprise data users will evaluate
NakliData primarily on whether “local,” “anonymized,” “session,” and “refresh”
mean exactly what they say.

### 2. Incremental Refresh is not a dependable shipped capability

The production flow cannot establish its first fingerprint baseline, and
refresh source IDs do not match lineage source IDs. Even if those two issues are
patched in isolation, confirmation reruns cells without first remounting changed
local bytes.

For warehouse users, call this **change detection** only after it has an
end-to-end test:

`baseline → source bytes change → source remount → dependent cells rerun in order → result changes`

Use **freshness check** only when the remote source exposes an actual validator
such as ETag, Last-Modified, snapshot ID, or a bounded content hash.

### 3. “Data never leaves the tab” needs one precise exception statement

Core compute is local, but cloud sidecar jobs can send SQL, column names, sample
values, and result rows to the configured provider. This is user-initiated BYOK
behavior, not covert upload, but the absolute claim is inaccurate.

Recommended copy:

> Data and compute stay in your browser unless you explicitly connect a remote
> source, enable the OSM basemap, or invoke a cloud sidecar action. Before each
> cloud action, NakliData shows the provider and payload categories.

Non-public semantic types should be redacted or blocked from cloud prompts by
default.

### 4. The target-market source picker over-promises

The first-run picker gives files, protocols, Iceberg, and an unshipped bridge
equal visual weight. Reorganize it by readiness:

- **Local data:** file, folder.
- **Object storage:** HTTPS, S3-compatible.
- **Catalogs:** Iceberg REST — disabled until verified.
- **Warehouse compute:** advanced bring-your-own bridge — clearly labelled.

Add branded Databricks or Snowflake cards only when the complete setup is
installable and tested. A card should not be a glossary alias for an unfinished
generic protocol.

### 5. Product truth is drifting from registries

Public copy still says 48 semantic types across four domains; the current
taxonomy file contains 204 unique types across 29 domains. Docs say eight
sidecar jobs while the registry defines ten, and Settings describes only the
original three.

Generate capability counts and support tables from canonical registries during
build. This removes a recurring credibility problem without adding runtime
bundle weight.

## Recommended delivery order

1. Contain the agent-redaction and malformed-load criticals.
2. Introduce complete session/source/cell artifact ownership.
3. Rebuild Incremental Refresh around canonical identity and source remount.
4. Make anonymized and CSV exports fail closed across every path.
5. Disable misleading Iceberg cards and relabel Compute Bridge.
6. Correct privacy and capability copy.
7. Ship one verified platform path, then add its branded preset.

For the first platform path, prefer the option that can be tested without
introducing a large shell dependency. Keep connector code lazy and protect the
remaining 9.4 KiB bundle headroom.

## Vocabulary and jargon to cover

Use a portable NakliData term as the primary label. Accept vendor vocabulary as
search aliases and show it in connector-specific help.

| NakliData term | Databricks vocabulary | Snowflake vocabulary |
| --- | --- | --- |
| Catalog / database | Catalog | Database |
| Schema / namespace | Schema | Schema |
| Compute endpoint | SQL Warehouse | Virtual Warehouse |
| Semantic model | Metric View | Semantic View |
| Metric / measure | Measure | Metric |
| Dimension | Dimension | Dimension |
| Relationship | Relationship / join | Relationship |
| Grain | Grain | Grain |
| Data-quality check | Expectation | DMF / expectation |
| Classification | Data classification / governed tags | Semantic and privacy categories / tags |
| Open-table catalog | Unity Catalog Iceberg REST | Open Catalog / Polaris |
| Source change token | Snapshot / table version | Snapshot / refresh metadata |

Useful discovery and documentation aliases:

- lakehouse, data warehouse, catalog, namespace, schema;
- managed table, external table, view, materialized view, Dynamic Table;
- Delta Lake, UniForm, Apache Iceberg, Iceberg REST Catalog, credential vending;
- external location, volume, stage, external volume;
- fact, metric, measure, dimension, relationship, cardinality, grain, join path;
- verified query, synonym, business term, owner, certified, deprecated;
- profile, expectation, DMF, completeness, uniqueness, validity, freshness,
  anomaly, semantic drift;
- data contract, schema evolution, lineage, impact analysis;
- governed tag, privacy category, semantic category, PII, PCI, PHI;
- medallion architecture, bronze, silver, gold, CDC;
- OAuth, service principal, PAT, key-pair authentication, role;
- DBUs, credits, resource monitor, query profile, query history.

Use operational terms only where a real feature exists. Do not imply support for
Unity Catalog, Open Catalog/Polaris, Genie, Cortex Analyst, Snowpark, Lakeflow,
RBAC/ABAC enforcement, masking policies, row-access policies, production
scheduling, or continuous monitoring until each path is implemented and
verified.

## Positioning recommendation

Lead with jobs where NakliData is already credible:

- inspect a partner/vendor file before warehouse ingestion;
- classify and profile governed extracts without uploading them to another SaaS;
- review a semantic model or data contract before promotion;
- create deterministic quality checks from semantic types;
- export a portable data dictionary, anonymized sample, report, or contract.

Avoid competing on warehouse-scale compute, governance enforcement, or
orchestration. The sharper message is local validation and portable semantics at
the boundary of the customer’s existing Databricks or Snowflake estate.
