# NakliData consolidated recommendations

Date: 29 July 2026
Audience: product, engineering, design, and go-to-market
Target users: Databricks and Snowflake analysts, data stewards, analytics
engineers, platform teams, and governance teams

This document consolidates the product review, forward-pass technical audit,
role-based walkthrough, positioning recommendations, terminology map, and
delivery sequence from 25–28 July 2026.

## Goal execution status

Started 29 July 2026.

- **Phase 0 containment — complete.** Agent value access now fails closed and
  accepts only direct, one-table, provenance-traceable projections. Complete
  `.naklidata` validation and normalization happens before live mutation;
  autosave is suspended during restoration. Adversarial unit tests, destructive
  load/reload browser coverage, the 1,401-test suite, and production smoke are

- **Phase 1A ownership — complete.** Source/cell/session/VFS artifacts now have
  explicit lifecycles; names are collision-safe across source kinds; workspace
  boundaries clear runtime and connection state; session deletion and Start
  Fresh remove all owned storage; folder restores preserve table IDs. See
  DECISIONS EN.
- **Phase 1B exports — complete.** SQL results now retain strict direct-column
  provenance in local snapshots; ambiguous, derived, legacy, and unknown
  columns fail closed. User types carry sensitivity and cannot shadow bundled
  ids. Standard, anonymized, and golden CSV paths share one formula-safe policy,
  including the 5,000/5,001-row boundary. Anonymized data and manifest

- **Phase 2 correctness — next.** Rebuild Incremental Refresh around canonical
  identity, atomic remounts, truthful run outcomes, and commit-on-success
  fingerprints.

## Executive recommendation

Position NakliData as:

> A browser-local inspection, semantic-contract, and data-quality workbench
> beside Databricks or Snowflake.

Lead with jobs NakliData can already perform credibly:

- inspect partner, vendor, and operational files before warehouse ingestion;
- classify and profile governed extracts without uploading them to another SaaS;
- review semantic definitions and data contracts before promotion;
- create deterministic quality checks from semantic types;
- perform bounded, explicitly initiated analysis;
- export a portable data dictionary, anonymized sample, report, or contract.

Do not position it as another warehouse, governance-enforcement platform,
orchestration service, or turnkey Databricks/Snowflake connector yet. Iceberg
mounting is unavailable in the current build, and Compute Bridge does not ship
with a supported server, image, installer, or branded warehouse adapter.

## Work already completed

The 28 July walkthrough closed three recommendations:

- Workspace changes now drop mounted-source relations, materialized
  `cell_<id>` relations, and DuckDB virtual-filesystem registrations before a
  new session or file is loaded. The smoke harness verifies that outgoing cell
  relations do not appear in a fresh session.
- S3, Iceberg, and Compute Bridge dialogs now explain user-visible behavior,
  supported authentication, result boundaries, and limitations instead of
  exposing internal terms such as “Slice 3b”, `httpfs`, Arrow IPC, CSP, and
  repository plan paths.
- Data-dictionary export no longer leaks a false `unknown action` warning into
  the global dispatcher; the smoke test guards against regression.

These fixes improve the current boundary but do not replace the broader
session/source/cell ownership work below.

## P0 — release-blocking trust and data-integrity work

### 1. Make agent value access fail closed

The agent surface currently redacts returned values by output column name.
Aliases, expressions, concatenations, CTE aliases, and duplicate names can
therefore escape the source-column sensitivity map. If the sensitivity layer is
unavailable, value-bearing queries and range enrichment can proceed with raw
values.

Recommendations:

- Refuse value-bearing agent queries and range enrichment until the sensitivity
  layer is ready.
- Allow values only for direct, public, provenance-traceable projections in the
  first safe contract.
- Refuse or redact sensitive, derived, duplicate-name, and ambiguous
  projections.
- Attach source-column provenance to result metadata rather than reconstructing
  it from output names.
- Test missing taxonomy state, aliases, expressions, CTE aliases, duplicate
  names, and unclassified columns.

### 2. Make `.naklidata` loading atomic

A malformed file can pass shallow validation, clear the active workspace, fail
during nested restoration, and leave autosave able to persist the partial state.

Recommendations:

- Fully validate and normalize the complete file—including assignments,
  settings, and every discriminated cell shape—before mutation.
- Stage restoration away from the live workbook and engine.
- Suspend autosave while applying a file.
- Commit the restored state atomically or roll back to the byte-identical prior
  workspace.
- Add a destructive-load regression covering workbook state, engine catalog,
  session snapshot, and result snapshots.

### 3. Complete workspace and artifact ownership

The recent session fix covers major workspace boundaries, but full ownership
still needs to include source names, cell deletion, credentials, result
snapshots, semantic stores, abort controllers, and runtime caches.

Recommendations:

- Prefer a per-session DuckDB schema or a single explicit artifact registry.
- Give every source and VFS object an opaque, source-owned identifier; do not
  derive ownership from filenames or user aliases.
- Prevent same-name and sanitized-name collisions across file, folder, URL,
  S3, Arrow, and generated sources.
- Drop a cell’s engine relation when the cell is deleted.
- Clear S3 connection settings when a source is removed and at every workspace
  boundary; use source-scoped named secrets when supported.
- Delete all session-owned snapshots, result rows, fingerprints, handles, and
  source secrets on session deletion and Start Fresh.
- Reconcile restored folder tables by stable origin/name and preserve their
  persisted table IDs.
- Add a boundary matrix covering new, switch, delete active/inactive, Start
  Fresh, load file, remove source, delete cell, and same-name remount.

### 4. Make anonymized and CSV exports fail closed

Anonymized result assignments can be reconstructed from ambiguous global column
names. Unknown or custom semantic types can default to `keep`. CSV formula
neutralization also differs by export path and disappears for large or
specialized exports.

Recommendations:

- Carry source-column provenance into every result and export.
- Use the strictest sensitivity tier when provenance is ambiguous.
- Default unproven, unknown, and custom columns to redact rather than keep.
- Add sensitivity to user-defined semantic types.
- Prevent user-defined IDs from replacing bundled semantic-type IDs.
- Use one formula-safe CSV writer, or neutralize every textual field and header
  before all standard, anonymized, and golden CSV `COPY` paths.
- Test duplicate names, aliases, custom types, unknown provenance, formula
  headers and values, and the 5,000/5,001-row boundary.
- Make data plus anonymization manifest atomic, or clearly report that the
  manifest was omitted and offer retry.

## P1 — core correctness and safety

### 5. Rebuild Incremental Refresh as a real end-to-end capability

The current flow cannot reliably establish its first fingerprint baseline,
uses different identities for refresh and lineage, does not remount changed
local bytes before rerunning cells, and can count failed cell runs as successes.

Recommendations:

- Use one canonical source/table identity across mounts, lineage, refresh,
  persistence, and tests.
- Persist the first successful scan as the baseline.
- Remount changed bytes atomically before recomputation.
- Run affected cells in topological dependency order.
- Make `runCell()` return a discriminated success/failure outcome.
- Accept a new fingerprint only after every required remount and rerun succeeds.
- Keep the old baseline when refresh fails.
- Call the feature “change detection” until the complete path is verified.
- Use “freshness check” only when a source supplies ETag, Last-Modified,
  snapshot ID, content length, or a bounded content hash.
- Report validator-less HTTP sources as uncheckable, never “up to date.”
- Test: baseline → source bytes change → remount → dependent cells rerun in
  order → result changes.

### 6. Harden taxonomy execution

User-defined regular expressions run synchronously and can wedge the taxonomy
worker despite the advertised time budget. Worker boot and requests also need a
single lifecycle and deadlines.

Recommendations:

- Reject unsafe regex constructs or use a bounded regex engine.
- Add one in-flight worker boot promise.
- Add persistent failure handlers and deadlines to classify/set-type requests.
- Terminate and recreate failed workers and reject all pending requests.
- Skip trimmed-empty strings before numeric coercion.
- Compare normalized SQL base types and explicit compatible families instead of
  substring matching.
- Let user types support numeric/date SQL families, or match any compatible
  family by default.
- Test hostile imported regexes, concurrent boot, dead workers, numeric user
  types, blanks, and `INTERVAL` versus `INT`.

### 7. Resolve the agent write contract

The documented Settings control does not exist, while the latent `runCell`
capability can execute an existing cell without per-action confirmation.

Recommendations:

- Remove `runCell` from the shipping agent catalog, or require one-time
  confirmation bound to the exact cell ID and content hash.
- Keep proposals editable and un-run.
- Treat any session-wide setting as permission to propose, never permission to
  execute.
- Bound or reject every row-producing agent SQL form, including `TABLE`,
  `VALUES`, `FROM`-first, and `DESCRIBE`, before materialization.
- Add tests proving that no agent path runs a cell without explicit human
  confirmation.

### 8. Harden the browser/service boundary

Recommendations:

- Replace generic same-origin service-worker caching with an explicit
  static-asset allowlist.
- Bypass authenticated, credentialed, API, `private`, `no-store`, non-200, and
  partial responses.
- Disable Cloudflare observability to honor the no-telemetry/no-error-reporting
  policy and verify the deployed dashboard state.
- Clean up every partially created engine, connection, worker, bootstrap URL,
  and field after any boot failure.
- Persist folder handles only after the first successful table, or remove them
  on empty/all-failed scans.
- Wrap temporary export files in `try/finally`.
- Run dependency-advisory checks in trusted CI where registry access is
  permitted.

## P1 — product truth for Databricks and Snowflake users

### 9. Make privacy language precise

“Data never leaves the tab” is too absolute. Cloud sidecar jobs can send SQL,
column names, samples, and result rows to the configured provider. Remote
sources and OSM tiles are also explicit network actions.

Recommended copy:

> Data and compute stay in your browser unless you explicitly connect a remote
> source, enable the OSM basemap, or invoke a cloud sidecar action. Before each
> cloud action, NakliData shows the provider and payload categories.

Also:

- Show the provider and payload categories next to every cloud action.
- Redact or block non-public semantic types from cloud prompts by default.
- Avoid presenting a BYOK action as equivalent to fully offline operation.

### 10. Reorganize source choices by readiness

Recommended source-picker structure:

- **Local data:** file, folder.
- **Object storage:** HTTPS, S3-compatible.
- **Catalogs:** Iceberg REST—disabled until verified.
- **Warehouse compute:** advanced bring-your-own bridge.

Additional recommendations:

- Disable Iceberg table/catalog cards with an explicit current-build
  explanation; re-enable only after real URL and REST Catalog smoke tests.
- Label Compute Bridge “Advanced—bring your own compatible bridge endpoint.”
- Do not add branded platform cards until setup is installable and verified.
- When real, browse sources hierarchically:
  `catalog/database → schema/namespace → table/view`.
- Harden Bridge health checks around protocol identity, version, and
  capabilities.
- Add timeouts, cancellation, byte limits, content-type validation, bounded
  streaming, and structured partial failures to Bridge queries/catalog mounts.

### 11. Ship one verified platform path before broadening claims

Recommended order:

1. Databricks Unity Catalog through a verified Iceberg REST flow.
2. Snowflake Open Catalog/Polaris through a verified Iceberg REST and OAuth
   flow.
3. Packaged Databricks SQL Warehouse and Snowflake Virtual Warehouse bridge
   adapters.

Each setup should explain:

- workspace or account;
- catalog or database;
- schema or namespace;
- warehouse ID or HTTP path;
- role and read-only privileges;
- OAuth, service principal, PAT, or key-pair authentication;
- where SQL runs, what data crosses the boundary, and result-size limits.

Do not market direct warehouse connectivity while users must deploy an
undocumented custom bridge.

### 12. Generate product truth from canonical registries

Documentation and UI counts have drifted from the build: semantic types,
domains, sidecar jobs, supported formats, and product version are inconsistent.

Recommendations:

- Generate capability counts and support tables from canonical registries at
  build time.
- Update README, feature docs, status, Settings help, and competitive material
  together.
- Display the real release tag/build SHA, or remove the prototype-looking
  version.
- Retire claims that Databricks and Snowflake do not classify data.
- Differentiate through no-upload local analysis, business/domain semantics,
  evidence and confidence, portability, and deterministic non-AI workflows.

## P2 — onboarding and day-to-day UX

### 13. Deliver first value before asking for SQL

Recommendations:

- Replace “Browse example data” with “Try the demo” or a genuine example chooser.
- Decide explicitly between one coherent target-shaped example and a
  finance/events/logs workload picker.
- Generate one deterministic starter report, or provide one prominent Run demo
  action.
- Lead with classified fields, evidence, sensitive fields, unknowns, and
  suggested quality checks.
- Keep the demo deterministic and available without an AI key.

### 14. Improve responsive visibility and navigation

Recommendations:

- Keep primary actions visible at 1280 × 720.
- Collapse secondary header actions into labeled menus.
- Make source and schema rails collapsible or resizable.
- Separate connections/credentials, privacy/display, AI sidecar, and advanced
  agent configuration.
- Configure AI just in time; do not make it the center of onboarding.

Suggested information architecture:

```text
Workbook
├── Open / Save
└── Export / Embed

Data
├── Add data
├── Catalog browser
└── Refresh

Explore
├── Notebook
├── Query builder
└── Reports

Model
├── Semantic model
├── Relationships
├── Data quality
└── Lineage / impact

Configure
├── Connections and credentials
├── Privacy and display
├── AI sidecar
└── Advanced / agents
```

Do not expose Share unless a real, safe sharing mechanism exists.

### 15. Improve analytical and semantic presentation

Recommendations:

- Add display-only analytical number formatting so binary floating-point tails
  such as `1028093.3200000001` do not appear as financial values.
- Drive formatting from logical/semantic type while preserving raw values for
  SQL, exports, and precision-sensitive inspection.
- Group the 100+ semantic override types by business domain or role family.
- Keep search primary and show inferred, recent, and common types first.
- Render detector evidence as “column name matches” and “value shape,” with
  technical details available on demand instead of leading with
  `header_match`, `distribution`, and `length∈`.

## P2 — build the portable model and quality layer

### 16. Create a canonical multi-table semantic model

Measures, dimensions, and segments currently behave as useful notebook
expression macros, not a governed multi-table semantic model.

The internal model should contain:

- logical tables and source bindings;
- facts, dimensions, metrics, measures, and filters;
- relationships and join keys;
- cardinality, grain, time dimensions, and join paths;
- synonyms, descriptions, business terms, and verified queries;
- owner, certification, and deprecation metadata.

Build adapters around that model for:

- Databricks Metric View YAML;
- Snowflake Semantic View YAML;
- portable NakliData JSON or YAML.

Neither vendor format should become the internal source of truth.

### 17. Promote data quality into a first-class destination

Recommendations:

- Create a Data quality surface.
- Suggest deterministic checks from semantic classifications.
- Cover completeness/not-null, uniqueness, accepted values, valid ranges,
  format validation, referential validity, and semantic drift.
- Save checks as a reusable data contract.
- Export platform-ready definitions only where mappings are lossless.
- Use “Data quality check” as the portable label, with “Expectation” and “DMF”
  as platform aliases.
- Keep checks explicitly run or refreshed; do not introduce background polling
  or continuous monitoring.

## P2 — notebook, chart, lineage, and export completeness

### 18. Make notebook actions report truthful outcomes

Recommendations:

- Return a discriminated result from every cell run; downstream actions must
  stop and name failed cells.
- Bind suggested-report optional columns only from the selected table.
- Score required types independently by `(table,type)`.
- Materialize named `SHOW`, `DESCRIBE`, `PRAGMA`, `EXPLAIN`, and `SUMMARIZE`
  cells, or mark them explicitly non-referenceable.
- Gate native File System Access features separately from core WebAssembly so
  the documented Firefox file-input fallback can boot.

### 19. Bound chart and accessibility work

Recommendations:

- Put only the representative rendered subset in the hidden accessible table
  and announce truncation plus total row count.
- Render an actionable retry state when the Observable Plot chunk fails.
- Verify that an asynchronous chart result still belongs to the mounted cell
  before attaching it.
- Render negative bars to the left of a zero baseline and test mixed/all-negative
  series.

### 20. Make static exports complete and honest

Recommendations:

- Serialize or explicitly placeholder every shipped cell kind in static HTML:
  report, stats, Python, R, embedding, network, temporal, distribution, and
  future kinds.
- Preview omission counts before save.
- Include an export manifest describing included, rendered, and omitted cells.
- Preserve the original workbook creation timestamp and update only `modified`.

### 21. Clarify lineage editing

“Insert a cell on this edge” and delete-node currently change the lineage
visualization, not the executable notebook.

Choose one:

- relabel these actions as non-executable lineage annotations; or
- implement real notebook/source mutation and reference rewrites.

Do not leave visual edits looking like workflow edits.

## P3 — engineering hygiene and maintainability

Recommendations:

- Move the remaining hardcoded colors to `src/tokens/colors.ts`, with narrow
  documented exceptions for standalone export templates where needed.
- Make the engine-boundary gate directory-driven with explicit exceptions,
  including extractable taxonomy and sidecar-pure modules.
- Remove `listHandles()` until it has a production caller, or use it for
  conservative orphan-handle recovery.
- Keep all new connector, provenance, model-adapter, and validation code lazy or
  size-neutral. The verified bundle has only about 9.3 KiB headroom.
- Avoid adding a large SQL parser, connector SDK, or regex engine to the shell.
- Run build and bundle-size enforcement for every batch.

- Delta Lake, UniForm, Apache Iceberg, Iceberg REST Catalog, credential vending;
- external location, volume, stage, external volume;

## Recommended delivery sequence

### Phase 0 — containment

1. Make agent value access fail closed.
2. Make `.naklidata` loads fully validated, staged, and atomic.
3. Add adversarial and rollback regressions.

### Phase 1 — ownership and exports

4. Complete per-session/source/cell artifact ownership.
5. Close naming, credential, snapshot, folder-restore, and cell-deletion gaps.
6. Add result provenance and fail-closed anonymization.
7. Unify formula-safe CSV exports and manifest handling.

### Phase 2 — correctness

8. Rebuild Incremental Refresh end to end.
9. Harden taxonomy regex/worker lifecycle and agent row/execution bounds.
10. Harden service-worker caching and disable deployment observability.

### Phase 3 — product truth and first value

11. Correct privacy, capability, version, and competitive copy.
12. Disable unavailable Iceberg and relabel bring-your-own Bridge flows.
13. Improve demo onboarding, 1280-pixel visibility, source organization,
    semantic navigation, evidence labels, and numerical display.

### Phase 4 — verified platform value

14. Ship one tested Databricks catalog path.
15. Ship one tested Snowflake catalog path.
16. Add hierarchical catalog browsing.

### Phase 5 — differentiated model

18. Introduce the portable multi-table semantic model.
19. Add vendor import/export adapters.
20. Promote deterministic checks into reusable data-quality contracts.
21. Complete chart, lineage, notebook, and static-export truthfulness.

## Definition of done for every implementation batch

- Add focused regression tests for the failure mode.
- Run the affected path in the production build.
- For schema changes, render the schema panel, expand evidence, and apply an
  override.
- Run `npm run smoke`.
- Run `npm run test`.
- Run `npm run build` and keep `dist/index.html` at or below 768 KiB.
- Update `STATUS.md`.
- Log non-trivial decisions in `DECISIONS.md`.
- Run `npm run check` last.
