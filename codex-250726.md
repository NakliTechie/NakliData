# NakliData observations and recommendations

Date: 25 July 2026
Review focus: Product UX and positioning for Databricks and Snowflake users

## Overall assessment

NakliData has a strong technical core: browser-local DuckDB, semantic classification, evidence and confidence, deterministic report suggestions, assertions, lineage, portable exports, and a deliberately constrained AI sidecar.

The best category position is not “another data platform.” It is:

> A local inspection, semantic-contract, and data-quality workbench beside Databricks or Snowflake.

The strongest customer jobs are:

- validating partner or vendor files before warehouse ingestion;
- inspecting governed extracts without uploading them to another SaaS product;
- reviewing semantic definitions and data contracts before promotion;
- performing bounded exploration of Unity Catalog or Open Catalog tables;
- packaging a portable data dictionary, quality contract, semantic model, or offline report.

## Key observations

### 1. The target platforms are not visible in the product

The Add source dialog exposes generic Iceberg and compute-bridge choices, but no Databricks or Snowflake connection. Users must already understand how those protocols map to their platform.

The compute bridge is an advanced protocol surface and its packaged runtime remains separate roadmap work. It should not be presented as a turnkey platform connection yet.

### 2. First run stops before the product’s strongest value

The example action loads multiple data sets and an empty SQL cell. The user must find a suggested report, add it, and run it before seeing a meaningful result.

At 1280 × 720, the schema panel and suggested-report action overflow horizontally, placing an important action beyond the visible viewport.

The first experience should demonstrate classification, evidence, quality, and a useful result before asking the user to write SQL.

### 3. Product documentation does not consistently reflect the build

Some documentation describes 48 semantic types and four domains, while the current product has 193 types across 29 domains.

Release material refers to v1.7.0 while the visible UI and package version show v0.1.0.

Older competitive material says major platforms do not ship semantic classification. Both Databricks and Snowflake now provide sensitive-data classification, so this claim should be retired.

NakliData can still differentiate through:

- business and domain semantics across arbitrary local data;
- evidence and confidence for classifications;
- cross-platform portability;
- browser-local, no-upload analysis;
- deterministic workflows that do not depend on an AI provider.

### 4. The semantic layer is analysis-scoped

Measures, dimensions, and segments currently behave as expression macros. That is useful within a notebook, but it is not yet a governed, multi-table semantic model.

Databricks and Snowflake users will expect concepts such as:

- logical tables or models;
- facts;
- metrics or measures;
- dimensions;
- relationships and join keys;
- cardinality;
- grain and time dimensions;
- join paths;
- synonyms and business terms;
- verified queries;
- ownership and certification state.

### 5. Existing data-quality capabilities are under-positioned

Assertions, profiles, and semantic drift already cover useful quality jobs, but the UI does not translate them into Databricks expectations or Snowflake data-quality-check vocabulary.

The taxonomy could deterministically suggest:

- completeness and not-null checks;
- uniqueness checks;
- accepted values;
- valid ranges;
- format validation;
- referential validity;
- semantic drift comparisons.

These checks should remain explicitly run or refreshed. Continuous background monitoring would conflict with NakliData’s product constraints.

### 6. Source and settings architecture are implementation-led

Eight equally weighted source choices mix files, protocols, catalogs, and advanced infrastructure.

Catalog contents are flat instead of following the hierarchy familiar to warehouse users:

`catalog or database → schema or namespace → table or view`

The Settings modal is dominated by AI-sidecar configuration while also containing privacy, map, provider, model, and API-key controls. The core product works without AI, so AI configuration should be just-in-time rather than central to onboarding.

### 7. The product is close to its bundle ceiling

The production bundle measured 756.4 KiB against a 768 KiB limit, leaving approximately 11.6 KiB of headroom.

New dependencies should be treated as high risk. Prefer existing primitives, lazy feature code, or size-neutral replacements.

## Recommendations

### Priority 1 — Fix first value and responsive visibility

- Replace Browse example data with Try the demo or an actual example chooser.
- Use one coherent target-shaped example rather than three unrelated domains.
- Generate and run one deterministic starter report, or present one prominent Run demo action.
- Lead with classified fields, evidence, sensitive fields, unknowns, and suggested quality checks.
- Keep primary actions visible at 1280 × 720.
- Collapse secondary header actions into labelled menus.
- Make source and schema rails collapsible or resizable.

### Priority 2 — Establish a trustworthy product truth layer

- Generate capability counts from one canonical manifest.
- Update README, feature documentation, status, and competitive documents together.
- Display the real release tag/build SHA or remove the prototype-looking version.
- Replace “competitors do not classify data” with the defensible no-upload, cross-platform, business-semantics differentiation.

### Priority 3 — Add verified platform presets

Add explicit source cards only after each connection works end to end:

- Databricks Unity Catalog through its Iceberg REST interface;
- Snowflake Open Catalog or Polaris through its supported Iceberg REST and OAuth flow;
- later, Databricks SQL Warehouse and Snowflake Virtual Warehouse through packaged, branded bridge adapters.

Each setup should provide connector-native guidance for:

- workspace or account;
- catalog or database;
- schema or namespace;
- warehouse ID or HTTP path where applicable;
- role;
- OAuth, service principal, PAT, or key-pair authentication;
- required read-only privileges.

Do not market a direct warehouse connection while the user still needs to deploy an undocumented custom bridge.

### Priority 4 — Build a portable semantic model

Introduce an internal canonical model containing:

- logical tables and source bindings;
- facts, dimensions, metrics, measures, and filters;
- relationships, keys, cardinality, grain, and join paths;
- synonyms, descriptions, business terms, and verified queries;
- owner, certified, and deprecated metadata.

Build adapters around that model for:

- Databricks Metric View YAML;
- Snowflake Semantic View YAML;
- portable NakliData JSON or YAML.

Neither vendor format should become NakliData’s internal source of truth.

### Priority 5 — Promote data quality into a product destination

- Create a first-class Data quality surface.
- Suggest checks from semantic classification.
- Save checks as a reusable data contract.
- Export platform-ready definitions where mappings are lossless.
- Label the concept as Data quality check, with Expectation and DMF as platform aliases.

### Priority 6 — Reorganize navigation

Suggested information architecture:

```text
Workbook
├── Open / Save
├── Share
└── Export / Embed

Data
├── Add data
├── Catalog browser
└── Refresh

Explore
├── Notebook
├── Query builder
└── Reports

Model
├── Semantic model
├── Relationships
├── Data quality
└── Lineage / impact

Configure
├── Connections and credentials
├── Privacy and display
├── AI sidecar
└── Advanced / agents
```

## Platform vocabulary to support

Use one canonical cross-platform term, then show connector-native aliases in setup, search, help, imports, and exports.

| NakliData term | Databricks term | Snowflake term |
| --- | --- | --- |
| Catalog / database | Catalog | Database |
| Schema / namespace | Schema | Schema |
| Compute | SQL Warehouse | Virtual Warehouse |
| Semantic model | Metric View | Semantic View |
| Metric / measure | Measure | Metric |
| Dimension / field | Dimension | Dimension |
| Data quality check | Expectation | DMF / expectation |
| Classification | Data classification / governed tags | Semantic and privacy categories / tags |
| Open-table catalog | Unity Catalog Iceberg REST | Open Catalog / Polaris |

Additional useful search and documentation terms:

- managed table, external table, view, materialized view, Dynamic Table;
- Delta Lake, UniForm, Iceberg REST Catalog, credential vending;
- external location, volume, stage, external volume;
- fact, metric, measure, dimension, relationship, cardinality, grain, join path;
- verified query, synonym, business term, certified, deprecated;
- profile, expectation, DMF, completeness, uniqueness, validity, freshness, anomaly;
- data contract, semantic drift, lineage, impact analysis;
- governed tag, privacy category, semantic category, PII, PCI, PHI;
- medallion architecture, bronze, silver, gold, CDC, schema evolution;
- OAuth, service principal, PAT, key-pair authentication, role;
- DBUs, credits, resource monitor, query profile, and query history.

Use branded operational terms only in help or connector-specific flows when the corresponding capability is genuinely supported.

Do not claim support for Genie Agent, Cortex Analyst, Snowpark, Lakeflow orchestration, RBAC/ABAC enforcement, masking policies, row-access policies, production scheduling, continuous monitoring, or warehouse-scale compute until those capabilities exist.

## Recommended delivery order

1. Repair first-run value and 1280-pixel responsiveness.
2. Correct capability counts, versioning, and competitive messaging.
3. Ship a verified Databricks Unity Catalog preset.
4. Ship a verified Snowflake Open Catalog/Polaris preset.
5. Add hierarchical catalog navigation.
6. Build the portable multi-table semantic model and vendor adapters.
7. Promote assertions and profiling into data-quality contracts.
8. Package and test direct SQL/virtual warehouse bridge adapters.
